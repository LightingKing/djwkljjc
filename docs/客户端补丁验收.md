## Android 14/15 安装策略增量（target24）

原包的 `targetSdkVersion` 为 22。为满足 Android 14/15 对低 target SDK 的安装策略，新增清单
`client-patch/patches/ljjc-offline-target24-2.0.4.json`，只把解包后的
`apktool.yml` 中 `targetSdkVersion: 22` 精确替换为 `targetSdkVersion: 24`。专项测试和 dry-run
均已通过；随后使用独立的本地临时签名库完成真实构建：

- 输出：`client-patch/output/target24/ljjc-offline-target24-2.0.4-universal.apk`
- 输出 SHA-256：`8e63b130cb925adb2c690f64b6a2802d4c4e223f1bf9db843ca4635bf6d2639d`
- 报告：`client-patch/output/target24/ljjc-offline-target24-2.0.4-universal.json`
- `apksigner verify --verbose`：v1、v2、v3 均为 `true`。

target24 只改变安装元数据，没有改动 `TXApplication`、TPShell、任何 native 库或完整性逻辑。
它不能据此宣称已经可玩。为了避免清除原有 API28 测试实例的沙盒存档，另建了隔离的
`LJJC_Target24_API28`（`emulator-5564`），只在该新实例安装 target24 包并执行冷启动。

## 工件验收脚本

新增 `dev/verify-client-artifact.py`，把工件摘要、签名、包元数据和冷启动证据写成
可复核 JSON。它不会安装、卸载、清除数据，也不会改写 APK。对 target24 工件的静态
验收结果保存在 `dev/target24-artifact-verification.json`：

- SHA-256 与 `8e63b130cb925adb2c690f64b6a2802d4c4e223f1bf9db843ca4635bf6d2639d` 一致；
- 包名 `com.tencent.tmgp.fcicv`、版本 `59162`/`2.0.4`、`targetSdk=24`；
- `apksigner` v1/v2/v3 均验证通过，签名者数量为 1；
- 静态工件检查通过，但没有把它写成可玩客户端。

随后在隔离实例上用 `--serial emulator-5564 --cold-start-runs 5` 运行了冷启动工件检查，结果保存在
`dev/target24-cold-start-api28.json`。设备端 SHA-256 与 target24 APK 的
`8e63b130cb925adb2c690f64b6a2802d4c4e223f1bf9db843ca4635bf6d2639d` 一致，签名和包元数据均通过；
5 次启动命令都返回 0，但应用进程随后以 clean exit code 4 退出，故冷启动验收为失败。
原始 logcat 保存在 `dev/target24-api28-logcat.txt`。这确认 target24 安装策略没有解决
TPShell/Unity 初始化阶段的退出，但没有把另一份签名包的行为归因到 target24，也没有绕过完整性校验。

## MSDK 取证和离线 shim

空补丁安装到 API28 后，应用会在 `AppDelegater.onCreate` 调用 `WGPlatform.Initialized` 时出现：

```text
java.lang.NumberFormatException: For input string: "3000000000"
com.tencent.msdk.stat.DeviceInfo.getCpuInfo
com.actgames.fci.AppDelegater.onCreate
```

进程随后以状态 4 退出。这个结果已保存到 `client-patch/output/api28-logcat.txt`。

为验证 M1.4 的本地适配边界，清单 `client-patch/patches/ljjc-offline-sdkshim-2.0.4.json` 只替换 `AppDelegater.smali`，让 MSDK/Midas/TMSDK 的生命周期回调为空实现，不改 Unity 游戏逻辑。构建结果：

- 输出：`client-patch/output/sdkshim/ljjc-offline-sdkshim-2.0.4-universal.apk`
- 输出 SHA-256：`ed8faa55696990ec695259796132d4c3d9fefaa27f80bcea92a0e6c2b640ce65`
- 报告：`client-patch/output/sdkshim/ljjc-offline-sdkshim-2.0.4-universal.json`

安装 shim 后，`NumberFormatException` 和 MSDK 初始化日志消失；Unity 启动约 1 秒后进程仍退出。清单显示应用类是 `com.actgames.fci.tx.TXApplication`，其父类为 `com.tencent.tpshell.TPShellApplication`，这是独立的完整性/反篡改链路。相关日志保存于 `client-patch/output/api28-sdkshim-logcat.txt`。

## 当前结论

- M1.2 流水线已具备可重复的真实构建证据；输入 APK 没有被覆盖。
- MSDK 的已知启动崩溃已定位，并有可回滚的 manifest 驱动 shim。
- G1 仍未通过：重签名包在启动阶段被 `TPShellApplication` 链路终止。没有关闭、删除或伪造反作弊/签名保护，也没有把这个包宣称为可玩版本。
- 后续应在合规的本地适配范围内确认 TP/TPShell 是否存在官方离线初始化入口；如果只能通过绕过完整性保护才能启动，应保留阻塞记录，不把绕过作为修复。

## M1.10 本地沙盒支付边界

已新增 `client/local-sandbox-iap.lua` 运行时适配。它只在本地游客和精确的
`http://127.0.0.1:19080` 账号服务器同时成立时包装 Lua 层 `IAPHandler.Purchase`：
确认框确认后调用 `fci/purchasetouch`，再把服务端返回的 `local-sandbox:` 交易令牌
提交到 `fci/purchasedelevery`，最后刷新本地资源绑定并广播购买完成事件。适配不调用
原生 `m_iap:Purchase`，不读取或发送真实平台回执，也不改写 TPShell、签名或反作弊
逻辑；非本地账号仍回退到原始购买函数。

该文件目前由 REA/Lua 运行时加载，未通过 `build.py` 写入 FCI 保护资源。由于 target24
和 sdkshim 工件仍在 TPShell 完整性链路阶段退出，客户端购买 UI 尚未在真实 APK 上验收。
服务端下单、一次性令牌、拒绝远程回执和重复发货保护已有自动化测试，不能把源文件静态
验收写成端到端可玩证明。
