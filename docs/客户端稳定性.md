# 客户端稳定性诊断

## 当前结论

游客登录和本地服务端链路已经完成，当前可复现的闪退发生在 Android 11 x86 模拟器的系统音频层。它不是游客账号、Auth、WebSocket 或本地接口失败。

复现方式是：启动原版客户端，使用运行时 Lua 注入显示游客入口，勾选协议后点击“游客登录”。请求完成后客户端进入主城初始化，随后主线程退出。

## 证据

Bugly NDK tombstone 位于模拟器应用目录：

`/data/user/0/com.tencent.tmgp.fcicv/app_bugly/tomb_1793118246700.txt`

同样的崩溃还出现在 `tomb_1793116675769.txt`、`tomb_1793116796751.txt`、`tomb_1793117040419.txt` 和 `tomb_1793117093353.txt`。最新一次复现时间为 2026-10-27 16:24:06，摘要如下：

```text
ABI: x86
signal: 11 (SIGSEGV)
#00 /system/lib/libbase.so
#01 /system/lib/libmedia.so android::MediaPlayer::setDataSource(int,long,long)+54
#02 <unknown>
```

重复复现时服务端仍记录完整成功链路：`AccountSession`、`EntryReg`、`Account`、`Auth`、`Dir`、WebSocket `CsConnect/CsLogin`、`/fci/login` 及主城初始化接口均返回 200。相关记录在 `analysis/ljjc-local/requests.jsonl`。

## 已排除项

- 游客账号没有使用过期的硬编码 entry；每次都走 `AccountSession → EntryReg → Account → AccountSession → Auth`。
- TPNS 新 watchdog 兼容设置已经写入 `com.tencent.tpus.enableNewWd=0`，崩溃栈也不在 watchdog。
- 原版 APK 没有被修改，登录按钮和本地协议只通过启动器的 Frida Lua late injection 提供。
- 尝试在运行时屏蔽 `SoundManager`、`MediaPlayer` JNI 和 native 方法后，系统会在 `MediaPlayer` 析构阶段再次 SIGSEGV，说明直接替换音频方法会破坏对象生命周期，不能作为稳定修复。

## 安全修复路线

按风险从低到高：

1. 使用 `LJJC_ARM64_API30`：本机已经存在该 AVD，配置为 `arm64-v8a`。需要为 ARM AVD 准备对应架构的 Frida server 和启动配置，然后在不清除账号数据的前提下复测。
2. 使用 API 28 的 ARM/x86 AVD：Android 11 的 x86 `MediaPlayer.setDataSource` 是当前已知触发点，API 28 可用于区分系统音频回归问题。
3. 仅作为实验参数，在新建或复制的 AVD 上加入 `-no-audio`，确认无音频输出时是否仍触发同一调用。该参数尚未作为默认配置写入启动器。
4. 如果所有模拟器架构都复现，应回到资源侧检查触发该调用的音频资源和文件描述符，再决定是否只禁用具体 BGM 资源。

以上路线都保留原版 APK、游客认证和本地沙盒账号，不绕过客户端保护，也不伪造支付成功。

## 复测要求

每次复测应重新运行 `local-server/ljjc/launch-local.ps1`，不要直接点击 APK 图标。直接启动不会执行本地游客按钮注入，因而会出现“再次打开没有登录按钮”。复测时保存最新 tombstone、`requests.jsonl` 时间段和模拟器 ABI，避免把登录故障与系统音频崩溃混在一起。

## 冷启动诊断增强

`dev/cold-start-check.ps1` 仍然只执行 `am force-stop` 和 `monkey`，不会清除
应用数据或卸载包。自 schema version 2 起，它在每次检查前记录设备
`ro.product.cpu.abi`/`ro.product.cpu.abilist`、API level、
`ro.dalvik.vm.native.bridge`、主机架构和启动完成标志；每次启动另外记录
进程是否仍存活以及 logcat 中的 clean-exit/进程退出线索。

这让以下情况可以区分：

- ADB/模拟器环境没有启动；
- 32 位转译器存在或缺失；
- 应用仍在前台且没有崩溃；
- 应用被 TPShell/系统以 clean exit 终止；
- 普通 Java `FATAL EXCEPTION` 或 native 崩溃。

本机的 `LJJC_ARM64_API30` 预检还显示，x86_64 主机上的 QEMU2 不支持 ARM64
system image（`Avd's CPU Architecture 'arm64' is not supported ...`）。这条
限制不能通过客户端补丁解决，应作为环境阻塞记录。
