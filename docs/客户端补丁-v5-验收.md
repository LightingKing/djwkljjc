## 付费接口契约

接口：`GET /fci/purchase-activity-info/`，返回 JSON 对象，由现有 FCI HTTP 层编码。
根对象内是 `mp_info.utp_mpinfo_detail`，其中始终包含两个数组：

- `rank_info`：每档一行，`num` 是迷子数量字符串；未首充的 `send_ext` 是非空字符串，已用档位必须显式 `""`。
- `range_info`：每档一行，`num` 同上；`coin` 为数组，第一项 `send_num` 为普通赠送数量字符串（没有则 `"0"`）。

原版以 `PurchaseInfo.count` 取活动信息，不以人民币价格取值。
客户端在 0.1 秒延迟之后请求，防止 PurchaseVip.Start 清空列表；成功时 `JsonE` 后交原解析器，失败时传 `"{}"` 并仍广播刷新事件。
每次 FinishPurchase 会重新读取活动状态，首充角标据服务器状态消失。

## 版本协议接线

纯函数 `server/core/patch_versions.py:select_patch_manifest` 不读文件、不修改输入：

- 同一 APK 基线：只返回 `entry.version > client.patch` 的条目，按版本递增。
- 同版或客户端更新：返回空 history，保留 manifest 顶层版本。
- 缺少版本参数：保留原完整历史，兼容旧请求。
- 版本格式非法：抛 PatchVersionError，不能默认为已更新。
- 跨 APK 基线：仅允许已有 version=0 的整包跳转条目；不存在则抛 PatchVersionMismatch，禁止投递不同基线的 Lua 补丁。

`server.py` 已接线：成功返回纯 JSON 的 PatchVersionInfo，不包 RestfulResponse。显式force_patch优先于旧fixture，`/clientupdate/`和`/patch-version.json/clientupdate/`及其无尾斜杠变体都经过相同版本过滤。
`/app_version/` 继续走现有协议；原 Lua 只查看 `app_url` 决定公告，不认识假设的最新版本字段。

依据 `analysis/ljjc-local/bootstrap-static/patch-validation-disassembly.md` 的后续记录，
空 history 在完整前置启动状态下已能进入用户协议；“空 history 必然报错”的早期结论不成立。
同版客户端三次冷启动已实测，更新请求均为v5且没有第二次ZIP下载。

## 实机发现的既有登录限制

v4/v5本地密码账号冷启均会误走MSDK自动认证，失败后清空登录缓存，所以需手动重输；原Auth prefab限制密码12字符。错误密码的服务端error字符串与客户端读取error.code不匹配，可能触发本地化NullReference。已对v4包/源码与v5差异及Lua隔离复现交叉核对，三项均非v5新增。手动短密码登录成功，但自动登录、长密码和错误提示不标为验收通过，纳入后续P1。
