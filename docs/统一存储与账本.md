# 统一存储与账本（M3.2/M3.3 阶段产物）

本阶段建立了一个可版本化的 SQLite 存储底座和资源账本，供后续把账号、玩家、剧情、养成、活动、社交和沙盒支付逐步迁入同一个本地数据库。它只保存离线服自己的数据，不连接官方服务。

## 存储底座

实现位于 `server/core/storage.py`，入口是 `UnifiedStore(path)`：

- 数据库启用 WAL、外键约束、忙等待和 `synchronous=NORMAL`。
- `schema_migrations` 保存迁移版本，当前版本为 1；重复创建 `UnifiedStore` 不会重复建表或丢数据。
- 初始迁移覆盖账号、会话、玩家、资源、道具、角色、装备、关卡记录、任务、成就、活动、邮件、商店购买、抽卡记录、沙盒支付订单、社交关系和账本流水。
- `backup_to()` 使用 SQLite backup API 生成一致性备份；`restore_from()` 先做完整性检查，再原子替换目标文件。
- `transaction()` 使用 `BEGIN IMMEDIATE`，让一组资源变化和业务写入在同一事务中提交或回滚。

`accounts.py`、`game.py` 和 `economy.py` 现在支持可选的 `unified_store_path`。`server.py` 默认把三者接入 `state/local.sqlite3`，并在启动时执行兼容迁移；直接构造这些模块而省略该参数时，仍使用历史的 `accounts.sqlite3`、`game.sqlite3` 和 `economy.sqlite3`，因此旧测试和已有数据不会被隐式移动。相对路径按 `state_dir` 解析，也可以通过 `--unified-store-path` 或 `[server] unified_store_path` 指定其他位置。

兼容层只补列、索引和可空的旧会话字段，不会删除或复制旧库数据。若要使用旧库中的数据，需要显式选择对应旧路径；统一库是新服务实例的默认状态文件。

## 资源账本

实现位于 `server/core/ledger.py`，所有资源变更使用 `Ledger.grant()`、`Ledger.consume()` 或 `Ledger.apply_many()`：

- 账余额不会低于零；消耗不足抛出 `InsufficientResource`，事务会完整回滚。
- `max_balance` 可用于体力等有上限资源，超过上限的发放会被截断并记录实际变化量。
- 每次成功变更都会在 `ledger_entries` 留下操作类型、资源键、变化量、变更后余额、原因和时间。
- `idempotency_key` 使登录奖励、邮件领取、订单发货等重试场景不会重复发放。
- `apply_many()` 在一个事务内处理多种资源，适合购买、抽卡、结算等同时扣发场景。

## 验证

`tests/test_storage_ledger.py` 覆盖迁移幂等和 WAL、发放/消耗、重复请求、余额不足、批量回滚以及备份恢复。全量回归命令：

```powershell
python -m unittest discover -s tests -q
```

当前 M3 阶段完成的是底座、账本接口和三个本地模块的统一路径接入；仍未宣称所有官方服务端行为已经恢复。
