# 客户端解锁与资源解密计划

日期：2026-10-28。只列计划，不开始开发。

对应 ROADMAP 的两个阻塞项：
- **A — 去掉我们自己这份 APK 拷贝的 TPShell 完整性校验**（M1.3 / G1）。
- **B — 从运行中的原版客户端取出 Lua 解密密钥**（M1.5 / M2.3）。

## 前提与定位

- 《电击文库：零境交错》国服 2020-03 停服、台港澳 2020-08 停服，所有官方服务器都已关闭，游戏无法再购买或联机。
- 这是你自有的一份 APK 拷贝，做的是本机单机离线复活，只给自己玩。
- 因此这两步属于"让一个已停运的游戏在自己设备上重新跑起来"的互操作改造：A 让自己这份拷贝能在重打包后启动并连本地服务端，B 把我们设备上本来就有的游戏资源解出来读它自己的逻辑。两者都不触碰任何在运行的服务、支付或第三方。
- 原始 APK 始终只读，所有改动只落在拷贝上。
- 已有可复用的资产：Ghidra x86 工程、Il2CppDumper `dump.cs`、30 个已成功解出的运行时 Lua 转储、补丁流水线、API28/API30 x86 模拟器。

## A. TPShell 完整性校验

### 现状

重打包并重新签名后的包（哪怕是空补丁）在 `TXApplication`（父类 `com.tencent.tpshell.TPShellApplication`）初始化阶段 clean exit code 4。原生侧涉及 `libtprt`、`libtersafe`、`libxguardian`。目标是让**自己这份拷贝**在重打包后仍能正常启动到登录界面。

### A1 摸清壳做了哪些校验、在什么时机（调查，先于任何修改）

- 在**未修改的原版**上用 Frida 跟踪：`TPShellApplication.attachBaseContext/onCreate` 的调用链、`libtprt`/`libtersafe` 的加载点和导出、退出码 4 的实际触发位置。
- 用 Ghidra 工程定位：取签名/APK 哈希的调用点、读 classes.dex / so / assets 做校验和的位置、调试器/模拟器/root 检测、以及"校验失败 → 退出"的分支。
- 产出：`docs/TPShell校验点清单.md`，每个校验点记地址、触发时机、失败后果、证据。

### A2 给每类校验定方案（按优先级）

1. **优先满足而不是移除**：如果重打包后还能让某些校验自然通过（例如不触碰它校验的文件），就不动它。
2. **只在自己这份拷贝上中和强制路径**：对重打包后必然失败的完整性校验，把它的"失败即退出"路径改成不阻断启动。这是核心互操作改动，只作用于拷贝。
3. **脱壳重托管**（兜底）：如果 TPShell 和启动流程耦合太深改不动，评估把里面的 Unity/IL2CPP 应用从壳里取出来单独跑（不经过 TPShell 包装）。

每个校验点单独记录选哪种方案、为什么、改了哪里。

### A3 验收

- 自己这份补丁拷贝在 API28/API30 模拟器上冷启动 10/10 到达登录界面，不再 clean exit 4。
- 随后在手机上（M0.1 确认可装之后）重复。
- 全程不碰原始 APK，不碰任何在线服务。

### A4 风险

- TPShell 可能在原生侧重新派生校验，或分多层校验，A2 可能要来回几轮。
- 反模拟器检测可能要在模拟器侧或补丁侧单独处理。
- 每轮失败都留日志和原因，不把"装上了"当成"能跑"。

## B. Lua 资源解密密钥

### 现状

858 个 Lua 资源是 `FCI\0` 保护载荷，运行时由 libxlua/il2cpp 在内存里解成可加载的 Lua 字节码（`00 66 63 69 01 …`）。我们已经有 30 个运行时转储能反编译，证明解密发生在内存里。密钥就在我们自有的这份客户端里。目标是把自己设备上这份资源解出来，供离线重建读游戏自身逻辑。

### B1 定位解密例程

- 在原版上定位把 `FCI\0` 载荷变成可加载字节码的函数：从 libxlua 的加载入口和 il2cpp 的资源读取路径入手，结合 Ghidra 和已有 30 个转储的调用上下文。
- 产出：解密函数地址、算法形态、密钥/IV 来源的初判。

### B2 两条取回路线

1. **运行时抓取（成本最低，首选）**：在原版客户端上 hook 解密函数，直接把 858 个载荷的明文字节码导出；或只取一次密钥/IV。复用已经跑通 30 个的那套方法，扩到全量。
2. **静态还原（更持久）**：在 `libil2cpp`/`libxlua` 里确认算法和密钥，离线实现一个解码器。做成之后有一条可复现、不依赖每次开客户端的离线管线，供 M2.3 用。

两条可以并行：先用路线 1 拿到全量明文解除内容阻塞，再用路线 2 补可复现管线。

### B3 验证

- 解出的 Lua 必须能重新编译、往返一致。
- 和已知正确的 30 个转储逐一交叉核对，确保解码正确、没有伪造。

### B4 验收

- 858 个全部解成合法 Lua，归档到 `analysis/lua/`，M2.3 从 `blocked` 转为完成。
- 解出的配置/逻辑接着喂给服务端做内容还原（ROADMAP M2–M4）。
