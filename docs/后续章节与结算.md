# 后续章节与本地结算

`ChapterInfo.json` 中已经抽出的章节行（当前为 1–6，共 87 个普通/挑战 ID）会被本地副本状态机自动发现。每个行内的 `dungeonId` 都可以通过 `/fci/dungeon/` 进入，包含 5102、5903 等挑战型 ID；专项测试逐个验证入口返回 200。服务端仍只运行本地沙盒，不把缺失的官方表格当成已恢复。

`DungeonReward.json` 还记录了 2021、2022 两个 `notFight` 剧情转场。它们现在作为可选的本地场景入口支持进入和结算，结算不伪造战斗数据，也不发放经验；由于历史章节位置和奖励表不完整，它们不参与主线章节解锁门槛。

完整章节快照（`GET /fci/dungeon/chapter/full`，别名 `all`）会根据表中 `preChapterId` 和前一章 `keyDungeonId` 计算解锁状态。初始账号只显示第 1 章（及其 `storyChapterId` 别名）为已解锁；完成第 1 章的关键关卡 8 后，第 2 章才会变为已解锁，后续章节依次类推。为兼容旧的离线测试入口，普通 `/fci/dungeon/` 请求仍允许直接进入已抽出的关卡；需要严格检查时在 JSON 入口传 `enforceUnlock: true`（或 `strictUnlock: true`）。

普通和故事战斗共用 `FightActiveData`：客户端必须先 PATCH `/fci/dungeon/<uid>/active`，并报告终态 `winTeam=1` 或 `2`，之后 balance 才会结算。胜利会按本地明确的 EXP 规则写入玩家档案，失败不会发放 EXP。

入口 JSON 可以传 `difficulty: "normal" | "hard" | "challenge"`。5xxx 挑战型关卡在未指定难度时默认使用 `challenge`。同一关卡的普通、困难和挑战运行会按难度分别持久化，重复进入不会复用另一难度的活动 UID。结算 JSON 可以传 `stars`（0–3）和 `targetsDone`；目标 ID 限制为 1–3，未传星级但传目标时按目标数计算星级，胜负仍以 `FightActiveData.winTeam` 为准，缺少其它星级字段的本地胜利默认 3 星。星级、目标和难度保存在 SQLite，ChapterSummary 的普通/挑战星数会跨重启重算。

已完成的关卡可通过 `POST /fci/dungeon/<dungeonId>/sweep` 扫荡，支持 `difficulty` 和 1–10 次 `count`。扫荡只接受当前难度已有成功结算的关卡，奖励仅使用本地兼容经验，不代表官方掉落。章节详情下的 `GET/POST /fci/dungeon/<chapterId>/reward`（也接受 `rewards`、`claim`、`chest` 别名）提供首通、星级和宝箱领取；章节奖励表未恢复，因此这些奖励是明确标注 `sandbox` 的小额本地奖励。领取记录写入 SQLite，重复请求返回同一结果，不会重复发放。

导出的配置行和服务端独有的本地奖励都保留来源边界：没有恢复的后续官方表格不会被伪装成官方数据。
