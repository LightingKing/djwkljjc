# M1.8 客户端账号密码登录 —— 实测记录(2026-10-28)

用自建 Lua 编译/回包工具链改客户端登录,经热更新通道交付,实现**账号密码注册+登录**。

## 改动(源码级,经 `runtime/build_lua_bundle.py` 重编译回包)
- **`window/login/login`**(`runtime/login_m18.lua`):
  1. 实现被置空的 `ShowAccountAuthWindow` 桩:`this:SetData("accountAuth", {...})` + `WU.AcquireWindowAsync("Auth")`,打开 APK 自带但从未被调用的 `window/auth` 账号密码窗。
  2. `SetInitUI` 首次登录(无 accountCache)分支补 `ShowAccountAuthWindow("", "password", "", nil, nil)`,登录界面自动弹出账号密码窗。
  3. `clickSwitchAccount(true)` 也打开账号密码窗(切换账号入口)。
- **`window/auth/auth`**(`runtime/auth_m18.lua`):
  1. `GetEntryType` 放开为接受用户名(`^[%w_%.@%-]+$`,3–64)→ 返回 `"password"`(原版只认手机/邮箱)。
  2. `RequestAccountAuth` 改为 **JSON 两步**:`/AccountSession/`(ApiAccountSession wireformat 拿 token)→ `/Account/`(JSON `{entryType=password, username, password}` 注册或校验)→ `/Auth/`(JSON 同体,服务端 `_handle_auth` 的 JSON 分支转 `_handle_password_login`)→ 复用原 `OnAccountAuthResponse`(`_auth_result` 字段兼容)→ `OnAccountAuthSuccess`。
  - 效果:输入用户名+密码点确定 = 新账号则建、老账号则验,然后登录。无需改服务端(`accounts.py` 的 JSON 账号密码路径本就齐全并有测试)。

## 服务端(除下述 push 外无改动)
- `accounts.py` 的 `/AccountSession/`、`/Account/`(密码注册)、`/Password/`、`/Auth/`(JSON→密码登录)、`/ExistEntry/` 等本就实现并测过(scrypt、会话、游客绑定)。
- **push 一处改动**:`server.py` 的 `/push` 调 `handle_upgrade(..., allow_unmasked_local=True)`。原版客户端的 push WebSocket 发**未掩码**帧,服务端按 RFC 6455 拒绝(审计 `rejected | client frame is not masked`),导致登录后客户端复位、回不到城。本地回环/局域网个人服接受遗留客户端的未掩码帧(掩码帧仍可用),这正是 `push.py` 为遗留客户端预留的 opt-in。

## 实测(emulator-5560,经通道交付 `m18_login_auth.zip` = login+auth 双文件)
- 登录界面**自动弹出"登录"窗**(账号/密码/确定/取消),输入 `player01`/`secret123` → 确定。
- 服务端日志全 200:`/AccountSession → /Account → /Auth → /dirsvr/Dir`;`OnAccountAuthSuccess` 触发 → `ChangeLevel("SceneCity")`,出现登录后世界弹窗(离线退出战斗提示)。
- **push 修复后**:`push_connection` 为 `upgraded` 且不再 `rejected`,不再复位;进入**主城 bootstrap**,大量 `/fci/` 城内接口全 200(mail/task/activity/dungeon.chapter/guild/signboard/redpoint/...)。

## 主城加载打通:ApiChapterInfo.result protobuf 契约修复(2026-10-28)

登录后卡在加载页的致命错误 `Internal/protobuf.bytes: un-finished bytes (len 76 at offset 182)` 已定位并修复。

### 定位(Frida 钩 `pb.decode`)
- 唯一失败:`ApiChapterInfo.result`(`/fci/dungeon/chapter`,len=2991)。其余 `/fci/` 全部解码正常。
- Python + 服务端 descriptor 能完整解码该响应;客户端 lua-protobuf 失败 → 非字节损坏,是 schema 差异。
- 逐字段对比:客户端已加载 schema 与服务端完全一致(字段号/类型/嵌套)。
- 二分到 `ChapterSummary`(`ApiChapterInfo.result.summary`):其 `repeated uint32`(如 `#5 new_dungeon_id`,约 90 项)被服务端编码为 **unpacked**(`28 <v> 28 <v> ...`);客户端 descriptor 把这些字段标为 **packed**,lua-protobuf 只认 packed,于是把某个值(`0x4c`=76)当成 packed 长度来读 → 越界 "un-finished bytes"。
- 验证:把 `summary` 的 repeated 标量改成 **packed** 重新编码后,客户端 `pb.decode` 成功(`newDungeonId count=90`)。

### 修复(服务端,`game.py` `_message_pool`)
加载 descriptor 时,对所有消息(含嵌套)的 **repeated 数值标量字段**(int32/64、uint32/64、sint、fixed、sfixed、bool、enum、float、double)强制 `options.packed = True`,使 `SerializeToString()` 产出 packed,与客户端 proto3 风格的 descriptor 对齐。这是通用修复,覆盖所有端点(不只 chapter)。

### 结果(真机 emulator-5560)
- `player01` 账号密码登录 → 不再复位 → **进入新手开场剧情 → 章节剧情地图(第1章 倒霉的贩卖机,HUD:能量/硬币/迷子,章节节点 1-2/1-6/1-8 BOSS/训练)**。
- 登录后 `/fci/` 城内接口与 `/fci/tutorial/1`、`/fci/dungeon/<id>` 全 200,无 protobuf 报错。
