## 本地规则（D）

1. 全部活动常开，由独立 `data/server-only/activity-schedule.yaml` 配置；仍验证请求活动与关卡的所属关系、配置开放时间、星期、活动等级及 DungeonReward 的原始等级/前置/次数门槛。未修改原表 openTime。
2. 退休服务端的 DropInfo 概率表未恢复。活动战斗与现有本地材料副本一致，确定性发放 DungeonReward.dropDisplay，首通额外发 dropDisplayFirst；数量和资源 ID 使用原值。NPC 附加奖励按 SemiFixedDungeon.addtions 原值和实际 NPC 数量计算。此项只声明本地掉落策略，不声称还原原版概率。
3. 抓娃娃原权重分母使用 Misc.clawCraneTotalProbability，原消耗为 61001×1。退休的全服库存服务不存在，因此库存按账号独立，首次访问为第 1 日，原 ClawCraneStock 的供应累计至第 28 日，此后保持；原 isUnique 按账号终身记录。不可用奖项的概率区间成为空奖，不把权重转移到其他奖项。抽取顺序持久化并用账号与序号的 SHA-256 产生可重现随机数；原强制掉落阈值仍有效。
4. 抓娃娃原生 POST 没有交易 nonce。本地 Lua 增加分支，在请求发出前用 `WU.SetGameDataCache` 持久化按玩家隔离的计数器与 pending 交易号，通过现有 `GameRequest.Query` 发送最长 128 字符的 localRequestId。仅成功处理响应后清 pending；未收到响应的操作跨日、客户端或服务端重启仍重放同一回执，余额已耗尽也可恢复。无交易号的本地抽取拒绝扣费；本地测试工具仍支持 JSON requestId。原远端 POST 逻辑保留。依据：`common__windowutil.lua:1375`、`manager__configdatamanager.lua:50` / `:92` 原有 LoadFromFile / SaveToFile 绑定；`manager__restifizermanager.lua:44` 的 Query 用法。
5. 退休的圣诞随机任务选择服务未恢复。保留全部 29 条日任务、12 条周任务，分别每北京时间 06:00、周一 06:00 可领取一次，原始目标和奖励不变。原 refreshAfterGot 的即时重抽不复刻；不能通过重复领取刷材料。到期时间使用真实下一周期，周任务入口 11016 持续滚动。任务 95 的完整轮次、97 的首个死亡席位是按原枚举/参数和可用战斗记录实现的解释，未恢复退休服务端内部实现。

## 事务与回执

入口扣费、终态报告、胜利扣费、掉落、经验、材料、任务进度、星级领取、BuffShop 升级、抓娃娃消费/库存/回执都在 `LocalGame.atomic_mutation()` 内写入。圣诞任务领奖直接调用时也建立事务。任务推送在 after_commit 执行，回滚不推送虚假的进度。

已报告战斗的报告不可改写；结算回执持久化并重放，退出后的 active 请求被拒绝。同一未报告编队的重复进入只返回已有战斗，避免重复扣费。固定编队只能使用拥有的角色、合法原 NPC 位置和主战/援护槽位，拒绝重复 uid。星级只能 POST 领取，领取状态与资源原子提交。
