# 执行记录：Lua 解密 + TPShell 定位

日期：2026-10-28。只读原版 APK，未修改。对应计划 [客户端解锁与资源解密计划.md](客户端解锁与资源解密计划.md)。

## B — Lua 解密（已完成，完全离线）

### 结论

858 个 `FCI\0` 保护的 Lua 资源全部可离线解密、反编译，**不需要模拟器、Frida 或运行时 hook**。

### 过程

1. 发现仓库里 `analysis/ljjc-lua-extract/*.txt` 是**损坏的**——当初按文本读写，非 ASCII 字节全变成了 `?`(0x3f 占 46%)，作密文不可用。
2. 用 UnityPy 从 APK 里按字节无损重取 TextAsset(`m_Script` 用 `surrogateescape` 编码),得到真正的 `FCI\0` 密文。
3. 拿已有的 30 个运行时明文转储(`analysis/ljjc-local/lua-runtime/*.luac`,前缀 `00 66 63 69 01`)做已知明文,与无损密文配对,异或出密钥流。

### 还原出的变换

- 密文 = `"FCI\0"`(4 字节头) + 密文体;密文体长度 == 明文长度(长度保留变换)。
- 密钥流只用 4 个字节、周期 16,是一个 4 字节密钥按位置轮转:
  `keystream[i] = key[(i%4 + i//4) % 4]`。
- 密钥逐文件不同,但明文容器**永远**以 magic `00 66 63 69 01`(`\0fci\x01`)开头,所以
  `key[j] = cipher_body[j] XOR {0x00,0x66,0x63,0x69}`(j=0..3),**只凭密文即可求出**。
- 明文 = `cipher_body[i] XOR key[(i%4 + i//4) % 4]`。

### 验证

- 对 6 个有运行时转储的模块(ActorUtil、DungeonUtil、GuildUtil、MailUtil、SceneFight、Login)离线解码,与运行时明文**逐字节一致**。
- 全量解码 858/858,magic 全部正确,0 失败。
- 抽查新模块(ActivityUtil、EquipUtil、ItemUtil、FightHelper——不在原 30 个里)反编译,得到干净可读的 Lua 源码。

### 产出

- 解码器:[tools/decode_fci_lua.py](../tools/decode_fci_lua.py)(读 APK,不改)。
- 解码后字节码:`analysis/lua/*.luac`(858 个)。
- 审计:`analysis/lua/decode-audit.json`(每文件 key、长度、SHA-256、magic 校验)。
- 反编译源码:`analysis/lua-decompiled/*.lua`(全量批处理进行中,审计 `decompile-all-audit.json`)。

这解除了 ROADMAP 的 M2.3 和 M1.5 内容阻塞。`analysis/ljjc-lua-extract/` 的损坏副本应废弃,以 `analysis/lua/` 为准。

## A — TPShell 定位(静态 A1 完成;动态追踪待模拟器)

### 已确认(静态)

- 应用类 `com.actgames.fci.tx.TXApplication` 继承腾讯 `com.tencent.tpshell.TPShellApplication`。
- TPShell 加载 `libtprt`,TXApplication 另加载 `libtersafe`;原生库里还有 `libxguardian`。
- TPShell 声明的关键 JNI 方法:`initialize(...)I`、`nativeInit`、`initinfo()I`、
  `getEncType()I`、`getEncBlockSize()I`、`isBlockEncEnabled()I`、`getShellVersion`、`getGameId`。
- 这是一个 **DEX 加固壳(腾讯乐固/TP)**:真正的 `classes.dex` 是加密的,原生 `initialize()`
  在解包前校验 APK 完整性/签名。重打包或重签名改了 APK,`initialize()` 检测到不匹配即中止,
  对应之前观测到的 Unity 初始化后 `clean exit code 4`。
- 之前的失败证据(`docs/客户端补丁验收.md`):空补丁和 SDK shim 安装后仍在 TPShell 初始化阶段退出,
  与"壳在解包前校验完整性"一致。

### 动态验证 + 脱壳(已完成,2026-10-28)

环境:开发模拟器 `DJWK_LJJC_API30`(`emulator-5560`,x86,API30,headless),adb server 5038;
guest frida-server 17.24.3(`/data/local/tmp/ljjc-frida-server`,监听 127.0.0.1:27042,
adb forward 27052→27042);host `frida`/`frida-tools`/`frida-dexdump` 17.24.3。原版 APK 未改。

1. **原版能过壳**:启动未修改的原版,进程存活并进入 Unity,还尝试请求
   `http://127.0.0.1:19080/dirsvr/DirAccount`(本地服务未开故 Server Unreachable)。
   说明 `initialize()` 在原版上成功、真 dex 已解密加载。这正是脱壳的前提。
2. **脱壳(拿到真 dex)**:`frida-dexdump` 从运行中的原版 dump 出 **25 个解密后的真实 dex**
   (约 20 MB),保存在 `runtime/ljjc-real-dex/`。
   - `classes02.dex` 含全部真实应用类:`com/actgames/fci`、`TXApplication`、`MainActivity`、
     `com/tencent/msdk`、`tpshell`、`NativeInterface`,无缺失。
   - 这些就是壳在运行时解密出来的真实代码,是重建"无壳 APK"的输入。

### 结论与下一步

- **脱壳路线可行且已拿到产物**:真实 dex 已 dump。重建无壳 APK 的思路——用这 25 个真 dex 替换壳的
  stub `classes.dex`,去掉 `TXApplication`/`libtprt`/`libtersafe` 的加壳入口,改用真实 Application 类,
  这样包里没有壳,也就没有要通过的完整性校验。重建 + 跑通是下一步(属于改我们这份拷贝的构建阶段)。
- 环境保持可复现:`emulator-5560` 当前仍在运行供下一步使用;guest frida-server 常驻。原版 APK 始终只读。

### 重建无壳 APK 的尝试与发现(2026-10-28)

分析了真实应用的类结构和壳初始化,并确认了重打包的具体障碍。

**类结构(来自 `classes02.dex` 的 baksmali,`runtime/baksmali02/`)**

- `TXApplication` → `TPShellApplication` → `android.app.Application`。
- `TXApplication` 只重写 `onCreate`、`hideSystemNavigationBar` 等,**没有重写 `attachBaseContext`**;
  壳的解包全在父类 `TPShellApplication`。
- 关键门控:`TPShellApplication.attachBaseContext` 里,壳初始化**只在 `TPConfig.useShellMode()` 为真时**执行
  (`invoke-static TPConfig->useShellMode()Z; if-eqz ... :cond`)。`useShellMode()` 读取反射来的壳信息字符串。
  也就是说,让这个判断变成 false,就能干净地跳过壳初始化——这是最小的中和点。

**阻塞点:内存 dump 出来的 dex 是"快化(quickened/odex)"的**

- `frida-dexdump` 从内存 dump 的是 ART 优化过的 dex:大量 `invoke-virtual-quick vtable@N`、
  `return-void-no-barrier` 等 ART 专用操作码。**6415 个类里有 5235 个(82%)**含这类操作码。
- 这类操作码在脱离 oat/vdex 的独立 dex 里是非法的,ART 校验器会拒绝。所以这批 dump **不能直接**打进 APK 重打包。
- `classes02` magic 是 `dex\n035`、`classes17` 是 `dex\n039`,混合且快化。

### 下一步的三条路(择一)

1. **脱壳 + 干净 dex(推荐,继续脱壳路线)**:不从优化后的内存盲扫,而是 hook 壳加载 dex 的那一刻
   (`InMemoryDexClassLoader` / ART `DexFile::OpenMemory`),抓壳刚解密出来、ART 还没快化的**标准 dex**。
   拿到标准 dex 后:把 `TPConfig.useShellMode()` 改成返回 false(或中和 `TPShellApplication.attachBaseContext`),
   打进 APK、去掉对壳的依赖、重签名、装到 `emulator-5560` 验证能否越过加壳重打包死掉的那个点。
2. **脱壳 + 反快化(deodex)**:用 app 的 oat/vdex 把现有 dump 里的 quickened 操作码解析回标准调用。比路线 1 麻烦。
3. **中和原生校验(避开 dex 问题)**:保留原版壳结构(stub dex + 加密真 dex + libtprt),只在
   `libtprt` 的 `initialize()` 里把签名/完整性校验的失败分支patch 掉,让壳自己按正常流程解包。
   这样完全不碰 dex,也就没有 quickened 问题,但需要原生 .so 逆向和 patch(有 Ghidra 工程可用)。

当前结论:脱壳产物已拿到但需要"干净 dex"或反快化才能重打包;中和原生校验是不碰 dex 的替代路线。本轮没有产出可启动的无壳 APK,没有伪造构建结果。

### 路线 1 实测结果:壳的载荷本身就是快化的(2026-10-28)

按路线 1 做了加载时抓取:用 native hook 拦 ART 的 dex 加载函数
(`art::DexFileLoader::OpenCommon` / `ArtDexFileLoader::Open`,spawn-gated 在壳加载前装好),
抓到了 9 个 dex,其中 `runtime/cleandex/d_7351268_*.dex`(7,351,268 字节)含全部真实应用类
(`com/actgames/fci`、`TXApplication`、`MainActivity`、`TPConfig`、`msdk`),大小与内存 dump 的 `classes02`
(0x702be4)完全一致。

但 baksmali 之后发现:**这份加载时抓到的 dex 同样是快化的**——6415 个类里仍有 5235 个含
`disallowed odex opcode`,`TPConfig.useShellMode` 里依旧是 `invoke-virtual-quick vtable@16`。
`OpenCommon` 在验证/优化之前就被调用,它拿到的 base 指针内容却已经是快化的,说明**壳解密出来给 ART 的
载荷本身就是快化(odex)dex,不存在可直接抓的标准 dex**。因此路线 1 不能解除重打包阻塞。

### 修正后的判断

- **路线 1 作废**:壳不提供标准 dex。
- **路线 2(deodex 反快化)**:要把 5235 个类里的 `invoke-virtual-quick vtable@N` / `*-quick` 还原成标准调用,
  需要用 app 类层级 + bootclasspath 解析 vtable 索引。现代 ART 的快化 dex 反快化工具支持有限,较脆弱。
- **路线 3(patch libtprt,推荐)**:最干净。保留原版壳结构(stub dex + 加密载荷 + libtprt),重签名后
  只在 `libtprt` 原生层把签名/完整性校验的失败分支 patch 掉,让壳按原设计自己解包并运行它那份快化 dex——
  完全不碰 dex,绕开快化问题。代价是原生 .so 逆向:在重签名的拷贝上 Frida 跟踪 `initialize()`,定位
  校验点和中止分支,patch libtprt。

抓到的 `d_7351268` 和内存 dump 保留,供路线 2 需要时使用。

### 路线 3 实测结果:TP 壳的反篡改太早、太硬(2026-10-28)

- 用 `apktool` 以外的最小改动**重签名**了原版 APK(只换签名:zipalign + apksigner,CN=ljjc-offline,v2/v3),
  产物 `runtime/ljjc-resigned.apk`。
- 装上重签名版启动:进程在 **100ms 级**内就消失——`pidof` 连续 8 秒都抓不到稳定 pid,logcat 几乎无输出
  (静默退出,与之前记录的 clean exit 4 一致)。这证明壳在极早期(很可能是 `libtprt`/`libtersafe` 的
  native 初始化,甚至 JNI_OnLoad / .init 阶段)就检测到签名不符并退出。
- Frida 动态追踪受阻:`frida spawn` 对重签名包**始终超时**(壳干扰 spawn gating);进程存活太短,fast-attach
  也来不及(8 秒抓不到 pid)。原版包 spawn 正常,说明是重签名包的反篡改在更早、更硬地干预。
- 因此 route 3 要落地,只能对 `libtprt.so` 做**纯静态逆向**定位校验点再 patch;而 libtprt 是腾讯 TP 的混淆
  原生库,静态 RE 工作量大、不确定性高,属于多轮的独立工程。

### 三条路都撞墙后的结论与更好的方向

三条"改/脱壳客户端"的路都撞到 TP 壳本身的硬保护:路线 1 壳载荷即快化、路线 2 要反快化 6415 个类、
路线 3 反篡改过早且 libtprt 混淆。击败 TP 壳本身是个大工程。

**但 Track B 的突破打开了一条绕开壳的更干净的路**:FCI Lua 的加密是**对称 XOR**,已验证
**re-encode 出来和原密文逐字节一致**——也就是说我们能无损地**解码并重新编码**游戏的 Lua。而游戏自带
**热更新通道**(clientupdate / patch,见已解码的 `Window_Patch_Patch`、`Manager_RestifizerManager`)。
所以客户端的 **Lua 层**改动(登录界面改账号密码、服务器地址重定向、Lua 层的 SDK 处理)完全可以通过
**本地服务器用游戏自己的热更新通道下发重新编码的 Lua** 来实现——**不改 APK、不脱壳、不用 Frida**。
壳保护的是 native/dex 层,Lua 热更新是游戏的合法更新路径,不触发壳的完整性校验。

**建议**:暂停"脱壳/改 APK",改走热更新下发 Lua 这条路来做客户端改动(对应 ROADMAP 的 M1.5/M1.6/M1.8)。
需要真正改 native/dex(壳保护的部分)时,才回到 libtprt 静态 RE。
