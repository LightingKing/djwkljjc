## 2. 问题与修法

### H1（中）主题任务 60002–60005 把角色 ID 当关卡 ID

- **位置**：`tasks.py:627`，目标 67 的匹配是 `lambda p: not p or dungeon_id in p`。
- **原因**：这几个任务前三个 taskParam 是 ActorInfo 的角色 ID（1001/1401/2001、1008/2008/2114、1008/2008/2112、2113/2112/2114），其中 2112、2113 恰好也是剧情关卡 ID。
- **后果**：
  - “使用指定角色”的要求失效。
  - 不带这些角色打剧情 2112 三次，60004/60005 就直接完成。每天可领 2×40003、2×10003 和 20 点额外活跃。
  - 打 2800101 也会推进 60002/60003。
- **复现**：`probe_goal67.py`
- **修法**：
  - 把参数拆成两类：属于 ActorInfo 的 ID 是角色要求，必须和本次上阵队伍有交集；其余的才按关卡匹配。
  - 参数的含义以客户端任务表和 Lua 为准。
- **测试**：
  - 2112 撞 ID 的情况。
  - 不带指定角色时不推进。
  - 带指定角色时正常推进。

### H2（中）大额充值档：出处不实，兜底接口可放大到 648 万

- **位置**：
  - `data/client-tables/PurchaseInfo.json`：多了 2 行，rowCount 54；原版 `xlsx__purchaseinfo.lua` 只有 52 行，没有 Gem64800。
  - `economy.py:566-574,1678,1707,1768`
  - `mall.py:876`
- **后果**：
  - 非原版数据混进了标注原版出处的表，规则清单里也没有记录。
  - economy 兜底接受任何含 `648000` 的商品 ID，还乘上客户端传来的 count（最多 10）；mall 路径则特意不乘。
  - 兜底一单（productId `"x.648000"`、count=10）可得 +6,480,000。
  - mall 买一次 Gem648000 得 1,296,000（含首充翻倍）。
- **复现**：`probe_recharge.py`
- **修法**：
  - 先问用户是否保留这两档。
  - 保留的话：改成服务端本地 overlay（单独文件），`PurchaseInfo.json` 恢复成原版 52 行，写进规则清单，并说明首充翻倍是否适用于本地档。
  - 兜底接口：去掉 count 倍数（固定为 1），只接受自己表里的精确商品 ID，不再用子串匹配。
- **测试**：
  - 兜底拒绝伪造的 ID。
  - count=10 也只到账一次。
  - `PurchaseInfo.json` 行数与原版一致。
  - 本地档能正常购买。

### H3（中）组队副本胜利不发 8 个季节糖果

- **位置**：`dungeon.py:1600-1650`（`_team_balance`）只调用了 `modes._grant`，从没调用 `welfare_features.py:189` 的 `grant_battle_materials`。
- **原因**：现有测试 `test_welfare_periods.py:169` 直接调用福利方法，没有走真实的组队流程，所以测试通过不代表功能正常。
- **复现**：`probe_team.py`。完整走一遍组队（进入 → 上报战斗 → 胜利结算）后，1016 仍为 0。
- **修法**：
  - `_claim_terminal` 之后，若胜利，调用 `grant_battle_materials(..., dungeon_type=10)`。
  - 把返回结果并入两份 resChange，然后再缓存回包。
- **测试**：
  - 端到端：组队胜利后 1016 增加 8。
  - 失败不发。
  - 重复结算不重复发。
  - 受活动期上限约束。

### H4（低）角色返礼领满 3 次后红点不消

- **位置**：每日上限只在 `game.py:1491-1512` 领取时检查。`profile_features.py:422-452` 的列表和 `events.py:664` 的登录红点仍然列出全部可领项。
- **复现**：`probe_present.py`。42 个可领，领 3 次后第 4、5 次回 409，但 GET 仍列出 39 个，红点一直不消。
- **修法**：`pending_role_presents` 在当天已领满时返回 `[]`；未领满时只返回剩余次数对应的数量。列表和红点共用这一份结果。
- **测试**：
  - 领满后列表为空、红点消失。
  - 06:00 重置后恢复。

### H5（低）竞技场上报胜利后退出，不记任务和培养

- **位置**：`tournament.py:471-494`，`_dungeon_quit` 是静态方法。退出时会关局并计入已上报的胜利，但跳过了 `_after_win`，所以任务 35/36 和培养的战斗胜利都不记录。正常结算路径在第 467 行会调用它。
- **复现**：`probe_tournament.py`
- **修法**：
  - 改成实例方法。
  - 胜利时用 `after_commit` 调用 `self._after_win(...)`，和结算路径一致。
- **测试**：
  - 上报胜利后退出：任务 35/36 和培养进度都已记录。
  - 之后再结算不重复记录。

### H6（低）印章补给邮件跨期可多领一份

- **位置**：`welfare_features.py:270-281`，补给邮件用 `expire_days=28, now=self._now()`。
- **后果**：活动期是从 `cycleStart` 起固定 28 天，而邮件从发出时起算 28 天。上一期末发出的邮件能拖到下一期，和下一期的邮件一起领，一期得 50 个，违反“每期一次”。
- **修法**：过期时间设为本期的 `cycleEnd`，例如 `ceil((cycleEnd-now)/86400)` 天，或直接传入绝对过期时间。
- **测试**：期末发出的邮件，过了 `cycleEnd` 就不能再领。

### H7（低，客户端补丁）LAN 清单里的结账地址判断没跟着修

- **原因**：`b8d808e`、`0206860` 只改了 `iaphandler-v13.lua`，而 `modules-lan.json` 打包的是 `iaphandler-lan.lua`。后者按完整 URL 精确比较，回环地址还缺 19082/19104。
- **修法**：
  - 统一成一份 IAP 适配。判断规则改为“回环或私有网段 + 本服务端口”，不再写死 `192.168.1.22`。
  - LAN 清单和正式清单使用同一份源码。
  - 需要重建补丁，从干净提交构建并核对哈希；按 Lua 编译、FCI 往返、可加载检查的流程走。
