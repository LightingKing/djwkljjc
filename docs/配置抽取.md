# M2.2 配置抽取记录

`tools/extract_runtime_configs.py` 将运行时导出的 JSONL、离线故事配置和 starter 配置整理成
`data/config/*.json`。每张表保留 `observedCount`、实际导出行数、来源文件、可重复推导的
`schema`、行内容 SHA-256 和 `completeness` 状态；`data/config/index.json` 汇总这些信息，方便后续配置驱动代码
拒绝把部分样本当成完整表。

当前输入包括：

- `config-samples-live.jsonl`
- `combat-config-live.jsonl`
- `starter-config-live.jsonl`
- `story-config.json`

当前生成 29 张表。`completeness=partial` 表示运行时导出只抓到了前 4 或前 6 行，
`observedCount` 大于 `rowCount`；`completeness=error` 表示客户端返回了
`attempt to get length of a nil value` 等错误；两者都不能当作完整配置。只有
`complete_observed` 表示在当前来源中行数和观测计数一致，仍不等同于官方服务端完整表。
后续从 APK/AssetBundle 补齐时，工具会以行数更多的来源替换当前样本，并保留来源和状态。

APK 清单中的配置资源和已抽取表是两个不同的证据层。运行下面的审计可重复核对两者：

```powershell
python tools/audit_config_sources.py `
  --inventory data/apk-inventory.json `
  --config-dir data/config `
  --output data/config-source-audit.json
```

当前清单记录了 208 个 `data/lua/xlsx` / `data/xlsx` 资源路径，归一化后对应 187 个不同表名；其中 19 个表名
同时有本地抽取结果，168 个只有 APK 资源路径。`data/config` 另有 10 个抽取表没有同名 APK
路径证据。清单还包含 4 个非 xlsx 的配置候选路径（如 `configproto` 和配置管理器），
它们只证明存在相关组件，不能当作表数据。审计报告把这三类分别标为
`asset_and_extracted`、`asset_only` 和 `extracted_without_inventory_asset`，并为每行固定写入
`decoded=false`；因此资源路径不会被误报为已解码配置。

`asset_only` 表仍是 M2.2/M2.8 的缺口。当前受保护的 `FCI\0` Lua/AssetBundle 载荷没有可验证的
解码密钥或字段定义，不能据此猜测行内容、补写完整表，或把资源数量当作已恢复的官方服务端数据。
报告同时保存 APK 清单哈希、资源路径和配置行摘要，便于后续拿到合法解码结果后做差异核对。

schema 是样本事实的摘要，不是猜测出来的 protobuf 定义：冲突类型会同时列在 `types`，
数组和对象只记录实际观察到的 `items`/`fields`。重新运行同一组输入会得到确定性 JSON。

`index.json` 和每张表都记录 `sourceRecords`（输入文件名、完整路径和 SHA-256），表记录另外
包含 `rowsSha256`。这些摘要用于发现输入漂移，不代表样本已经成为官方完整配置。工具同时支持
顶层 JSON 数组、带 `payload.values` 的导出，以及每行直接包含表对象的 JSONL。

当拿到第二份独立导出时，可用 `tools/verify_config_extraction.py` 逐表比较行摘要、schema
和完整行内容。只有两边都标记为 `complete_observed` 且行摘要一致时才会标记 `match`；
当前的 `partial`/`error` 表会标记为 `inconclusive`，不会被自动提升为完整配置：

```powershell
python tools/verify_config_extraction.py .\data\config .\other-export -o .\data\config-verification.json
```
